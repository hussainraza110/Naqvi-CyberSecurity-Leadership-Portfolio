# Security Leadership Operating Model

## Objective
Define services, accountability, capabilities, interfaces, and governance for a security function that enables business objectives while managing cyber risk.

## Design principles
- Organize around risk and business services, not only technologies.
- Separate oversight from operational execution where practical.
- Assign owners for security outcomes and residual-risk acceptance.
- Use federated delivery where local context matters, with enterprise standards.
- Reassess structure as strategy, threat, regulation, and technology change.

## Capability domains
| Domain | Accountability | Key interface |
|---|---|---|
| GRC | Policy, risk, regulatory mapping, assurance | CRO, Legal, Board |
| Architecture | Patterns, design review, exceptions | CIO, Enterprise Architecture |
| Operations | Monitoring, detection, response | IT operations |
| IAM | Identity lifecycle, privileged access | HR, application owners |
| Engineering | Security platforms and automation | Infrastructure, cloud |
| Resilience | Cyber recovery and exercises | BCM, DR |
| Product security | Secure SDLC and testing | Product engineering |
| Third-party security | Supplier assurance and concentration | Procurement, Legal |

## Service catalog
Publish owner, customer, intake, service target, evidence, escalation path, and cadence for architecture consultation, incident response, supplier review, risk exception, and security testing.

## Measures
Risk outcomes, service responsiveness, control coverage, delivery enablement, capability, and cost-to-serve. Avoid measuring success only by ticket closure or tool count.
